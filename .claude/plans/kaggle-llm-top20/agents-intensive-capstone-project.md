## Per-winner synthesis

### Concierge Agents, 1st: NewsPulse AI Agent (Andy Zhang, Shuai Tan, Vivien Li, Adelie.Yang)
[writeup](https://www.kaggle.com/competitions/agents-intensive-capstone-project/writeups/NewsPulse-AI-Agent), about 750 words (short). **Bank 8b covers** the 5-phase ADK design on Gemini 2.5 Flash, profile and history agents, search separated from fetch, the citation-enforcing LoopAgent, dispatch and feedback. New facts only:
- **User:** executives and C-suite leaders drowning in generic news alerts and wary of hallucinated or stale GenAI output; the success metric is **delivery in under 5 minutes** (writeup), which is why Gemini 2.5 Flash was chosen for all agents (latency plus long context for several full HTML articles in one pass).
- **8 agents** in total. A **Requirement Agent can pause to ask clarifying questions** when intent is ambiguous. The Historical-Recommender filters out news the user has already seen.
- **Grounding:** custom Python tools decouple Google Search (URLs only) from an "Executive Fetch Agent" that scrapes real HTML with BeautifulSoup rather than trusting snippets. The verification loop requires "100% of claims citation-backed" before approval.
- **Context hand-off:** Pydantic I/O schemas between agents to avoid "telephone game" context loss.
- **Observability:** a custom `logger_config` to trace hand-offs across the 8 agents, used to tune the verification loop. **Memory:** the Feedback Agent writes user critiques back into the profile constraints.
- **Evaluation:** none reported (no test set, no numbers). **Deployment:** not described in the writeup. Roadmap: scheduled runs, Bloomberg/internal sources, in-email feedback widgets, fetch retry/fallback, TTS audio briefs, multilingual.

### Concierge Agents, 2nd: FIL Content Agent System (Jason Harrison)
[writeup](https://www.kaggle.com/competitions/agents-intensive-capstone-project/writeups/fil-content-agent-system), about 1,100 words.

**Problem and user.** Content creation for a real site: the author's wife's waterfall-photography blog *Falls Into Love*. Each page took about 2 hours (30+ min research across AllTrails, recreation.gov, forums and park sites; 60+ min writing in the site's voice; 15+ min CMS publishing and SEO). Target: a 60-second chat inside the CMS ("Create a page for Cherry Creek Falls in Washington").

**Agent design (ADK).** A root agent orchestrates a router, a **4-step create pipeline** (check for duplicates -> research -> write -> publish, stopping early if a page exists) and **12 management tools** (publish, add to nav, move in hierarchy, list children). The research agent uses **`google_search_retrieval` grounding** and rejects fictional requests ("Sparkle Rainbow Falls": "I couldn't find credible sources"). Fuzzy matching ("primary" -> "Primary Nav"). Structured output with Pydantic; prompts kept in YAML.

**Multi-model strategy.** `gemini-2.0-flash` for intent classification (~200 ms) and `gemini-2.5-pro` for content generation; "reduces routing costs by 88%" (writeup).

**Tools / MCP.** A custom stateless **FastMCP server with 15 tools** covering the CMS lifecycle, hosted on **Cloud Run**. The CMS itself is Rails 8 + Hotwire with a chat UI; agents emit events streamed over ActionCable so users see step-by-step checkmarks instead of a 60 s spinner.

**Sessions / observability / eval.** ADK sessions keyed by `user_id` for event streaming; **OpenTelemetry to Cloud Trace**; **ADK `AgentEvaluator` with 8 test fixtures** (no pass rates reported).

**Deployment.** The fullest Google-cloud stack among the 12: **agent on Vertex AI Agent Engine, MCP server on Cloud Run**, three repositories (CMS, MCP, Agent). Demo: page creation about 35 s with 8 content blocks and SEO metadata; management actions about 2 s each (writeup). Roadmap: explicit multi-page creation, session persistence, surfacing citations, memory of past phrasing to avoid repetition.

### Concierge Agents, 3rd: AishIngAnalyzer (Aisha Sartaj)
[writeup](https://www.kaggle.com/competitions/agents-intensive-capstone-project/writeups/aishinganalyzer-cosmetic-ingredient-analyzer), about 580 words and **thin** (its Architecture and Build sections are images only); facts below marked (README) come from the [GitHub README](https://github.com/aishasartaj1/AishIngAnalyzer).

**Problem and user.** Consumers facing 20 to 40-ingredient cosmetic labels; manual research takes 20+ minutes per product and existing databases ignore individual skin type and allergies.

**Agent design: LangGraph, not ADK.** The only 1st-to-3rd winner in this capstone built on **LangGraph**. Four Gemini agents (README: **Gemini 2.0 Flash**): **Supervisor** (dynamic routing on state, retry management, max 2 attempts), **Research** (chooses tools by ingredient type and confidence), **Analysis** (personalised report adapting detail to user expertise and risk), **Critic** (validates, can reject and force a retry; routes `critic_rejected` back to Analysis).

**Tools / retrieval (README).** **Qdrant** vector search over sentence-transformers 384-dim embeddings; **Tavily web search fallback when confidence < 0.7** or the ingredient is missing; custom FastMCP tools `ingredient_lookup`, `safety_scorer`, `allergen_matcher`. **Memory:** Redis + LangGraph state. **Observability:** LangSmith traces. **Evaluation:** Ragas metrics plus Critic validation; README claims "Accuracy >95% (based on evaluation metrics)" without defining the test set.

**Own dataset.** Scraped from incidecoder.com, cosmeticsinfo.org and others; the writeup admits **only 64 ingredients** were scraped successfully (target 400+), and EWG Skin Deep ratings (the base of the safety score) could not be scraped because of JavaScript rendering and CAPTCHAs. The writeup also lists guardrails (input sanitising, output bounds, timeouts, cost caps, rate limits) as *future work*, i.e. not implemented.

**Deployment (README):** Streamlit UI on Streamlit Cloud (not Google Cloud). A notably candid entry: the "if I had more time" section is longer than the description of what was built.

### Agents for Good, 1st: Carbon Footprint Optimization Engine, CfoE (Sumit Kumar Guha)
[writeup](https://www.kaggle.com/competitions/agents-intensive-capstone-project/writeups/carbon-footprint-optimization-engine-cfoe), about 1,650 words; code is a single [Kaggle notebook](https://www.kaggle.com/code/sumitkumarguha/global-cfoe) ("no external repositories required"). **Bank 8b covers** the four agents, the non-LLM CalculationAgent and the HITL approval tool. New facts only:
- **Framing:** supplier ESG compliance in Source-to-Pay; "70% of corporate carbon emissions hide in supplier operations" and quarterly audits miss violations for months; the writeup names three failures it designs against: no real-time grounding, LLMs doing critical maths, unsafe autonomy.
- **Orchestration:** three `SequentialAgent`s: RootCoordinator -> DataCollectionTeam (MonitorAgent + built-in `google_search`, "agentic RAG" for adverse media and fines) -> AuditPipeline (Calculation -> Policy -> Reporting). Sequential was chosen for auditability; audit time 30 to 45 s, with ParallelAgent named as the upgrade path.
- **Deterministic agent, mechanism:** `DeterministicCalculationAgent(BaseAgent)` overrides `_run_async_impl` to **yield the `calculate_carbon_score` function call itself**, so the LLM never decides whether or how to score; identical inputs gave identical scores across 10 runs (writeup).
- **HITL mechanism:** `enforce_policy_hitl` is a `LongRunningFunctionTool` that calls `tool_context.request_confirmation()` when the ESG risk score is >= 0.80; ADK saves session state and pauses until a human resumes via the API (`ResumabilityConfig`). `InMemorySessionService` for state.
- **Observability:** `LoggingPlugin`, a custom `TraceVisualizer`, a `MetricsCollector` for cost, latency and success.
- **Evaluation (writeup):** **22 test cases in 6 categories** (critical 4, low 4, moderate 3, edge 4 including boundaries 0.00/0.80/1.00, asymmetric 3, real-world archetypes 4): 22/22 passed, HITL trigger accuracy 100%, average audit cost $0.002. These test the deterministic threshold logic, not LLM output quality. Business-impact table (quarterly -> real-time, 8 h -> 15 min review, false positives 35% -> <5%) is asserted without a stated source.
- **Deployment:** configs for both Vertex AI Agent Engine (`deployment_vertex_ai.yaml`) and Cloud Run (Dockerfile) included; the writeup does not claim a live deployment. **Model:** `gemini-2.5-flash-lite` (from the notebook; not stated in the writeup).

### Agents for Good, 3rd: Parallel Scholar (Eman Afi, Yousef Elsonbaty)
[writeup](https://www.kaggle.com/competitions/agents-intensive-capstone-project/writeups/parallel-scholar), about 1,400 words, mostly descriptive prose with no numbers; the body calls the project "Advanced Research Assistant Agent".

**Problem and user.** Researchers, students and under-resourced institutions doing literature search, trend analysis and citation formatting by hand.

**Agent design (ADK, hierarchical, 4 agents).** **Root Agent** orchestrates, delegates, synthesises a final report and writes to memory; **Researcher** calls the arXiv API, prioritising 2023 to 2025 papers and extracting titles, authors, dates, abstracts (truncated to 300 chars, "et al." for long author lists) and links; **Analyst** computes the publication-year distribution and draws ASCII charts; **Formatter** produces APA citations. Despite the title, the writeup does not describe an ADK `ParallelAgent` explicitly; it mentions "parallel research capabilities" only in the impact section.

**Tools.** Custom arXiv search tool with retry logic; citation formatter; **file-based persistent memory (JSON)** as a cross-session knowledge base, with different paths for local vs cloud (`/tmp`).

**Sessions / reliability / observability.** `InMemorySessionService` for multi-turn context; `nest_asyncio` for notebook event-loop conflicts; Python `logging`; `HttpRetryOptions` with exponential backoff for rate limits.

**Evaluation.** An automated heuristic scoring function checking that a response contains formatted lists, recent years, URLs, analytical content and memory-persistence confirmation. No results reported.

**Deployment.** Flask REST wrapper (chat + health endpoints, flagged development-only), ADK web UI, and code/docs for **Vertex AI Agent Engine** deployment (no live deployment claimed). Gemini model name not stated.

### Enterprise Agents, 1st: Chaos Playbook Engine (Alberto Martinez Zurita, alessandro-a.russo)
[writeup](https://www.kaggle.com/competitions/agents-intensive-capstone-project/writeups/new-writeup-1763223319877), about 940 words. **Bank 8b covers** the deterministic seeded chaos core (503/429 injection), the Gemini 2.5 Flash-Lite ADK `LlmAgent` with a `lookup_playbook` RAG tool, `AgentEvaluator` on a golden dataset, and 37.2% -> 97.0% success at a 20% tool-failure rate over 14,000 runs. New facts only:
- **Full results ladder (writeup, n = 14,000 simulated ops, "95% confidence, p < 0.01"):** baseline vs playbook success at tool-failure rates 0% 100/100, 1% 95.4/100, 3% 88.9/100, 5% 80.9/100, 10% 61.1/99.8, 15% 50.3/98.5, 20% 37.2/97.0. A second run used **280 real agent ops** against a random mock API. The headline framing: a 20% tool failure rate becomes roughly a 70% workflow failure rate without recovery. Claimed side effects: 60 orders recovered per 100 under chaos, zero double-charges ("97% reduction in data corruption"); the cost is **+59.8% latency**.
- **Test domain:** a `PetstoreAgent` (order workflow) whose dependencies are injected at runtime: `ChaosProxy` for fault injection and a **`CircuitBreakerProxy` that opens after 3 failures**; retries use jittered backoff against thundering herds.
- **Code-quality claims:** 100% strict type hints, `Protocol` interfaces (`ToolExecutor`, `LLMClientConstructor`), cognitive complexity < 8. Runs locally via `InMemoryRunner`.
- **Deployment:** none yet; Cloud Run with live Stripe/Google APIs is roadmap Phase 7, followed by a "Triple-Agent Comparison Lab", an observer "Agent Judge" that auto-writes playbook entries from production logs, and parametric testing of prompt playbooks.
- **Caveat:** the data-source links in the writeup point to a `chaos-playbook-lab` repo path, while 663531 links `chaos-playbook-engine`; the report files were not checked.

### Enterprise Agents, 2nd: Coderama (debasis dwivedy)
[writeup](https://www.kaggle.com/competitions/agents-intensive-capstone-project/writeups/coderama-reimagining-enterprise-software-deliver), about 1,000 words (a third of it install commands; architecture diagram is an image).

**Problem and user.** Enterprises whose software delivery spans separate teams with different structures, policies and even languages. Coderama simulates an SDLC run by agent "teams" that take a business goal through requirements, sprint planning, development and testing, "from months to days" (writeup, no measurement).

**Agent design: A2A between teams, MCP within teams.** The point of the entry is **A2A + MCP interoperability**: each team is a separate agent service speaking the **A2A protocol** (A2A Python SDK), and each team's internal tools are exposed by a **FastMCP server over stdio**. A **Host Agent** (ADK) routes requests dynamically to: **Requirement Gathering Agent** (asks clarifying questions, assumes nothing; the detailed requirement must be **approved by the user** before it is final), **Project Planning Agent** (splits the requirement into sprints so the developer agent is not overloaded), and **Software Development Agent** (itself several sub-agents that write, validate and test code **one sprint at a time, advancing only after user approval of each sprint**). A **Policy Enforcer** sanitises everything going to and from the user.

**Memory / observability.** In-session memory only (persistent memory is future work); per-agent INFO logs (`requirement_gathering.log`, `software_development.log`, `project_planning.log`) capturing tool calls, tool responses and LLM responses. Output is a downloadable project with run instructions and test cases.

**Model.** A single Gemini model serves all agents (name not given); a router sending planning to `gemini-pro` and generation to `gemini-flash` is future work.

**Evaluation.** None reported. **Deployment.** Local (uv, Docker listed in stack), Gradio frontend; no Cloud Run or Agent Engine. Future work: mTLS for A2A and MCP, context trimming per sub-agent, React UI.

### Enterprise Agents, 3rd: VeganFlow (Karthick Sothivelr)
[writeup](https://www.kaggle.com/competitions/agents-intensive-capstone-project/writeups/veganflow-autonomous-supply-chain-intelligence), about 930 words.

**Problem and user.** Store managers in vegan retail (short shelf lives, thin margins) juggling spreadsheets, vendor emails and POS data, causing stockouts and spoilage.

**Agent design: hierarchical delegation + A2A negotiation.** **Orchestrator ("Store Manager", Gemini 2.5 Pro)** delegates to **Inventory Agent ("Shelf Monitor", Gemini 2.5 Flash)** with direct **SQL access to a local SQLite store DB** (stock, sales velocity, expiry) and **Procurement Agent ("Negotiator", Flash)**, which reads **price targets from long-term memory** and talks to a simulated **ecosystem of 11 independent vendor agents over A2A** (HTTP), each with its own personality, pricing model and reliability score. Demo: "Check stock for Oat Barista Blend" -> 0.8 days of supply left -> Procurement recalls a $3.40 target, picks "Clark Distributing", opens an A2A handshake, rejects list price, counters with a 10% volume discount -> vendor accepts, **deal closed with no human involvement**.

**HITL.** None: fully autonomous purchasing. The writeup itself names a "Supervisor Check" (pause for approval when a deal is >15% above target) as V2 work.

**State / eval.** SQLite + ADK Session/Memory; **ADK Eval CLI regression tests against a golden dataset** (no results reported).

**Deployment.** Core agents on **Vertex AI Agent Engine**; the vendor ecosystem on **Cloud Run** to simulate a distributed network (writeup). Vendor ports are hardcoded; a dynamic Agent Card registry ("Yellow Pages for agents") is future work, as are time-series demand forecasting and shelf-camera vision.

### Freestyle, 1st: Daedalus, the Agentic Toolsmith (Milos Jovanovic)
[writeup](https://www.kaggle.com/competitions/agents-intensive-capstone-project/writeups/daedalus), about 1,550 words. **Bank 8b covers** the orchestrator-never-answers rule, ToolsmithPipeline (design, implement, test in ToolGym, register) and AgentSmithPipeline (sequential/loop/parallel/critic). New facts only:
- **Registries:** in-memory `InMemoryToolRegistry` and `InMemoryAgentRegistry`; the orchestrator (an `LlmAgent`) works only through `list_registered_tools`, `call_registered_tool`, `list_agent_pipelines`, `get_agent_pipeline_design`, `run_agent_pipeline`. Deterministic native tools (`get_weather`, `search_flights`) are registered at startup so simple tasks never trigger forging.
- **Toolsmith internals, plan -> generate -> test -> repair:** `ToolPlannerAgent` is a `LoopAgent` alternating `ToolSpecPlannerAgent` (LLM + `google_search`, emits a `ToolDesignModel` JSON: name, params, return type, success keys, error behaviour) and `ToolSpecReviewerAgent` (critiques or calls `exit_loop`) -> `InitialCodeGeneratorAgent` -> `ToolTestPlannerAgent` (reads existing golden tests to avoid duplicates; cases have `input_args`, `expected_keys`, `expected_contains`) -> **`ToolGymAgent` LoopAgent**: `ToolTestRunnerAgent` calls `run_tool_tests` (executes the generated function via `exec`) and sets `ok`/`needs_fix`; `ToolCodeFixerAgent` rewrites failing code. `register_dynamic_tool` validates, compiles and registers.
- **Golden Set as a growing eval suite:** passing fresh tests are persisted to a JSON `GoldenSetStore` and merged into future suites (`build_combined_test_suite`), so each new tool is regression-tested against all previously confirmed cases.
- **AgentSmith internals:** `MultiAgentPatternClassifier` picks `sequential`, `iterative_refinement`, `parallel_gather` or `generator_critic`; pattern-specific planners emit a Pydantic `AgentPipelineModel` (a `sub_agents` tree that may contain `parallel_group` nodes); `register_agent_pipeline` builds real ADK `LlmAgent`/`ParallelAgent`/`SequentialAgent`/`LoopAgent` objects, executed with `InMemoryRunner`.
- **Gaps the author names:** no persistence/versioning of forged tools, no guardrails or sandbox for generated code (it runs via `exec`), no ToolGym dashboards. No quantitative evaluation and no deployment described. Gemini model not named. Images made with Nano Banana; video narrated with AI Studio TTS.

### Freestyle, 2nd: AI Stock Prediction System, Multi-Agent A2A Architecture (Nishant Pithia, Vagge Sneha)
[writeup](https://www.kaggle.com/competitions/agents-intensive-capstone-project/writeups/ai-stock-prediction-system-multi-agent-a2a-archit), about 1,400 words. **Track move:** the writeup footer says "Track: Enterprise Agents", but it won 2nd in **Freestyle** (API and 663531), consistent with the host's right to move entries.

**Problem and user.** Analysts and investment firms who spend hours per stock across fundamentals, technicals, sentiment, macro and regulation; target: an explainable recommendation in under 10 seconds.

**Agent design: coordinator pattern over A2A.** A **Strategist Orchestrator** decomposes the request and calls, **in parallel** (`asyncio` + `aiohttp`, ADK `RemoteA2aAgent`), five specialist agents, each an **independent FastAPI microservice on its own port with an agent card at `/.well-known/agent-card.json`, A2A protocol v0.3.0 over JSON-RPC**: Fundamental (8001), Technical (8002, RSI/MACD), Sentiment (8003), Macro (8004), Regulatory (8005); then a **Predictor Agent (8006)** synthesises by **weighted signal averaging**. Each specialist returns a Pydantic signal and confidence (sample AAPL run: signals +0.40/+0.24/+0.47/+0.30/0.00 -> BUY, confidence 66%, medium risk, 4.18 s).

**Model:** Gemini 2.0 Flash for all 6 agents. **Tools:** custom wrappers for **Polygon.io** (prices, fundamentals, technicals, news), **FRED** (GDP, inflation, rates), **SEC EDGAR** (10-K/10-Q/8-K), **NewsAPI**, each with rate-limit handling and fallbacks. **Sessions:** `InMemorySessionService`.

**Evaluation.** No backtest and no accuracy measurement: "Accuracy: 65-70% confidence scores (realistic, not overfit)" reports the model's own confidence, not hit rate; a formal eval suite and historical backtesting are listed as future work. Speed 4 to 10 s per analysis (writeup).

**Deployment.** All agents Dockerised on **Cloud Run** (0 to 10 instances each), Cloud Build CI/CD, **Secret Manager** for API keys, Cloud Logging; Next.js frontend visualising each agent's signal live. Demo in `notebooks/kaggle_submission_complete.ipynb`. Future: Vertex AI Memory Bank, XGBoost in the Predictor, a risk agent.

### Freestyle, 3rd: StoryLand AI (Olga Ostrovskiy)
[writeup](https://www.kaggle.com/competitions/agents-intensive-capstone-project/writeups/storyland-agent), about 1,550 words.

**Problem and user.** Readers who want to visit the places of a book they loved (literary tourism) but face scattered blogs, film-location sites and forum debates (was Pemberley Chatsworth or Lyme Park?).

**Agent design (ADK, three phases with a human choice in the middle).** **Phase 1, metadata:** `book_metadata_researcher` calls a custom Google Books tool and `book_metadata_formatter` validates a `BookMetadata` schema, disambiguating titles (Kristin Hannah's *The Nightingale* vs a 1950s novel). **Phase 2, discovery:** a `SequentialAgent` running `book_context_pipeline` (setting, themes, period) and `reader_profile_agent`, then a **`ParallelAgent` of city, landmark and author-site pipelines**, each a researcher (built-in `google_search`) + formatter (Pydantic) pair, then `region_analyzer_agent`, which groups cities into practical travel regions with day estimates (5 regions for *Pride and Prejudice*). **Human selects a region.** **Phase 3:** `trip_composer_agent` builds a `TripItinerary` honouring budget, pace, museum interest and kids, reading discoveries via `get_discovery_data_tool`. Nine-plus Pydantic models throughout.

**Memory / context engineering (the most complete of the 12).** ADK **`DatabaseSessionService` on SQLite** (sessions survive restarts); each agent writes a named state key; preferences use the **`user:` prefix so they persist across sessions**; a `ContextManager` estimates tokens and applies **sliding-window compaction** while preserving system prompts.

**Observability / evaluation.** `structlog`, ADK `LoggingPlugin`, custom event monitoring over `runner.run_async()`. **125 pytest unit tests** plus an ADK eval with custom rubrics (book relevance, preference adherence, completeness, actionability, geographic accuracy, engagement); no scores reported.

**Model:** Gemini 2.5 Flash. **Performance (writeup):** about 50 s end to end (5 s metadata, 30 s parallel discovery finding 12 cities, 15 landmarks, 8 author sites; 15 s composition). **Deployment:** local only (CLI, notebook, `adk web`), free AI Studio key; no cloud deployment.

## Consensus vs divergence

**Table stakes:** ADK multi-agent composition with `SequentialAgent`/`ParallelAgent`/`LoopAgent`, Pydantic schemas between agents, Google Search grounding or a domain API tool, a video, a public repo, and a "why agents, not one prompt" section (the rubric's Pitch). Almost no one fine-tuned, and almost no one measured anything.

**What separated 1st place from 2nd/3rd** (4 track winners vs 7 others with sources): every 1st-place entry has a **mechanism that makes the LLM's output checkable**: NewsPulse's citation-gated LoopAgent, CfoE's LLM-bypassing calculator plus a pause-for-approval tool, Chaos Playbook's seeded 14,000-run experiment with a baseline, Daedalus's generate-test-repair ToolGym with an accumulating golden set. Infrastructure breadth did not decide places: **all three A2A entries and all three MCP entries placed 2nd or 3rd**, and the two entries with the fullest live GCP deployments (FIL, VeganFlow) are 2nd and 3rd. The 1st places were also the most self-contained single-repo builds (CfoE is one Kaggle notebook).

**Divergent choices:**
- *Autonomy vs approval:* VeganFlow closes purchase deals with no human ([writeup](https://www.kaggle.com/competitions/agents-intensive-capstone-project/writeups/veganflow-autonomous-supply-chain-intelligence)); CfoE argues "HITL is non-negotiable for enterprise" and pauses the whole workflow ([writeup](https://www.kaggle.com/competitions/agents-intensive-capstone-project/writeups/carbon-footprint-optimization-engine-cfoe)).
- *One model vs two tiers:* FIL routes with 2.0 Flash and writes with 2.5 Pro, claiming 88% lower routing cost ([writeup](https://www.kaggle.com/competitions/agents-intensive-capstone-project/writeups/fil-content-agent-system)); VeganFlow puts 2.5 Pro on the orchestrator only; NewsPulse uses 2.5 Flash everywhere for latency ([writeup](https://www.kaggle.com/competitions/agents-intensive-capstone-project/writeups/NewsPulse-AI-Agent)).
- *Distributed vs in-process agents:* Stock Prediction and VeganFlow run each agent as its own A2A microservice ([SP](https://www.kaggle.com/competitions/agents-intensive-capstone-project/writeups/ai-stock-prediction-system-multi-agent-a2a-archit)); Daedalus builds new ADK agents in memory at runtime ([writeup](https://www.kaggle.com/competitions/agents-intensive-capstone-project/writeups/daedalus)).
- *Sequential for audit vs parallel for speed:* CfoE deliberately stays sequential (30 to 45 s) for auditability; StoryLand and Stock Prediction parallelise research for latency ([SL](https://www.kaggle.com/competitions/agents-intensive-capstone-project/writeups/storyland-agent)).
