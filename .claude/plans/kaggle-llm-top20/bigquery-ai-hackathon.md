## Per-winner synthesis

### 1. TriLink (Generative AI 1st, $15k, David Babu)
Links: [GitHub hazardscarn/TriLink](https://github.com/hazardscarn/TriLink/tree/main), [video](https://youtu.be/xmQJxaG4Lyc). Bank covers the data simulation; added detail below.

**Problem and user.** Call-centre agents, managers and field technicians at a digital service provider whose useful data (transcripts, tickets, device photos) is unstructured. Pitch: the warehouse as the "central nervous system" of an AI-native company.

**Data.** Fully synthetic, fictional Ontario telco "TriLink": 100,000 customers (~75k mobile, ~75k internet, ~42k home security) across `customer_df`, `mobile_df`, `internet_df`, `security_df`; thousands of call transcripts generated by Gemini 2.5 Flash from each customer's profile, then rated by Gemini 2.5 Flash-Lite; two curated knowledge bases (175 business problems with solutions, 100 technical issues with resolutions); a support-ticket set with text plus customer-submitted device images. All datasets shipped in the repo so judges need not re-simulate; three setup notebooks (env + base data, vector-store embeddings, BQML models).

**Five "Actions" (all SQL in BigQuery, one notebook):**
1. *Proactive follow-up:* `AI.GENERATE_BOOL` triages yesterday's transcripts for follow-up need; `ML.GENERATE_EMBEDDING` + `VECTOR_SEARCH` against resolved past calls and the solutions KB; `AI.GENERATE` writes a personalised email with cross-sell. 370 of ~960 weekly calls flagged; cost about $0.0055 per email (writeup).
2. *Agent coaching:* for each call, `VECTOR_SEARCH` finds the 3 most similar calls handled by high performers (rating > 6); `AI.GENERATE` prompts extract positives, missed opportunities and coaching phrases, then aggregate per agent per week. Author notes `AI.GENERATE_TABLE` was possible but plain prompts gave more control.
3. *Churn retention:* XGBoost classifier trained in BigQuery ML, `ML.EXPLAIN_PREDICT` feature attributions turned into a plain-language "problem statement" by `AI.GENERATE`, embedded and vector-matched to the solutions KB, then a personalised retention email.
4. *Ticket triage (multimodal):* `ObjectRef` over GCS images + text description into `AI.GENERATE_TABLE` (Gemini 2.5 Flash) with a schema: device, hw/sw, urgency, `need_on_site_visit` bool, technician report, DIY steps. On 100 sample tickets 62% needed no visit (writeup).
5. *ADK agent:* Google Agent Development Kit root `LlmAgent` routing to two sub-agents (call-centre assistant, technician assistant), each with `FunctionTool`s wrapping the BigQuery workflows above.

**Evaluation.** No accuracy evaluation of the generated outputs; impact is a back-of-envelope ROI per action (e.g. $6.4M/yr truck-roll savings, $420k/yr retention, 2,600 to 5,200 manager hours/yr), all assumption-driven (writeup). Feedback/survey file attached (bonus criterion).

**Judges:** "demonstrates a variety of BigQuery AI.GENERATE functions ... a very clear impact for each one of the processes" ([612730](https://www.kaggle.com/competitions/bigquery-ai-hackathon/discussion/612730)).

**Matrix facts:** Gemini 2.5 Flash / Flash-Lite; AI.GENERATE, AI.GENERATE_BOOL, AI.GENERATE_TABLE, ML.GENERATE_EMBEDDING + VECTOR_SEARCH, ObjectRef, BQML XGBoost; agentic (ADK multi-agent); own synthetic data; no public dataset; BigFrames not mentioned.

### 2. The AI Patent Analyst (Generative AI 2nd, $9k, Veysel Serifoglu)
Links: [live Streamlit app](https://patent-search-analytics.streamlit.app/), [video 2.5 min](https://youtu.be/6WVi1cdd5fw), [GitHub](https://github.com/veyselserifoglu/bq-ai-patent-analyst), [Kaggle pipeline notebook](https://www.kaggle.com/code/fissalalsharef/bigquery-ai-the-patent-analyst-project) (published under a second account, fissalalsharef). Writeup itself is short (~900 words); the pipeline notebook was pulled to fill details. Bank covers the 4-stage pipeline; additions below.

**Problem and user.** R&D and IP teams who must read patent PDFs (text plus technical drawings) by hand to find functionally similar components.

**Data.** Public: 403 patent PDFs (197 English, the rest French/German) from Google's **Labeled Patents** public dataset at `gs://gcs-public-data--labeled-patents/*.pdf`, joined to `bigquery-public-data.labeled_patents.figures` (notebook).

**Pipeline (all in BigQuery):** (1) Object Table over the GCS PDFs; (2) remote model `gemini_vision_analyzer` = `gemini-2.5-flash` called via multimodal `ML.GENERATE_TEXT` to extract title/abstract and describe diagrams; (3) `AI.GENERATE_TABLE` with an "expert analyst" prompt builds a nested component / function / interconnection graph; (4) `ML.GENERATE_EMBEDDING` with `gemini-embedding-001` produces two vectors per component (patent context, component function), blended by a SQL UDF `VECTOR_WEIGHTED_AVG` with **0.7 function / 0.3 context** weights, then `VECTOR_SEARCH`. Front end: Streamlit with semantic search, applicant portfolio bubble chart (portfolio size vs breadth vs complexity) and a components-per-patent histogram as a data sanity view.

**Evaluation.** No retrieval-quality metric or baseline; impact is an ROI model: 605 expert-hours and >$90k manual vs 15 min and <$20 pipeline cost, ">4,500x ROI", throughput ~0.6 to ~1,600 patents/hr (writeup + notebook).

**Judges:** "uses AI.GENERATE_TABLE to generate a knowledge graph ... clear reduction with a significant ROI advantage" ([612730](https://www.kaggle.com/competitions/bigquery-ai-hackathon/discussion/612730)).

**Matrix facts:** gemini-2.5-flash + gemini-embedding-001; ML.GENERATE_TEXT, AI.GENERATE_TABLE, ML.GENERATE_EMBEDDING + VECTOR_SEARCH (no vector index mentioned), Object Table over PDFs (multimodal), public dataset Y; no agent; no BigFrames mentioned; live demo Y.

### 4. SpeakAura AI (Vector Search 1st, $15k, team SpeakAura.AI)
Authors: shafi5110, biddahari. Links: [deployed Cloud Run app](https://speakaura-389325321804.us-central1.run.app/), [demo video (Google Drive)](https://drive.google.com/file/d/1lpUcgnvlzZrJZyoTl_yHbjskoPLSi4LY/view?usp=drive_link), [GitHub](https://github.com/hariprasath0622/speak-aura-ai), [Medium post](https://medium.com/@hariprasath0622/speakaura-ai-revolutionizing-speech-therapy-with-ai-8cd2484a5b02). Bank has a one-paragraph summary; model stack and SQL below are new.

**Problem and user.** People who stammer (~70M worldwide, 11 to 12M in India, per cited Stuttering Foundation / STAMMA figures) plus their therapists and schools; therapy is costly and progress is hard to measure.

**Data.** User-recorded speech audio (no external speech corpus named) and therapy PDFs / clinical guides as a knowledge base; course catalogue embedded for recommendations. No dataset sizes given.

**Models (as BigQuery remote models):** Chirp speech-to-text (`transcribe_model`), `gemini_2_5_flash` for reading scripts and therapy plans, `gemini_embedding_001`, and a Document AI `layout_parser_processor`.

**Pipeline.** Audio to GCS to an Object Table, then **`ML.TRANSCRIBE`** (Chirp) to word-level transcript tables; disfluency markers (pauses, repetitions, prolongations, fillers, severity score) computed in SQL + Python; transcript embedded with `ML.GENERATE_EMBEDDING`; `VECTOR_SEARCH` (top_k) over `analysis_results_embeddings` returns similar past sessions with their metrics and therapy plans (admin/therapist view); `AI.GENERATE` with `output_schema => 'therapy_plan STRING'` writes plans and read-aloud scripts; therapy PDFs go through **`ML.PROCESS_DOCUMENT`** (layout parser chunking) and are embedded with `task_type = RETRIEVAL_DOCUMENT` to ground a therapy chat; **`AI.FORECAST`** projects a fluency score (100 - 100 x severity) over sessions for the progress dashboard.

**Evaluation.** None: no detection accuracy for disfluencies, no retrieval metric, no user study. Impact claim "reduces therapist prep time by 40%+" (writeup), plus a comparison table vs existing apps (image).

**Judges:** "demonstrated BigQuery vector search capabilities using the transcripts to look for similar historical cases ... impact and value statistics" ([612730](https://www.kaggle.com/competitions/bigquery-ai-hackathon/discussion/612730)).

**Matrix facts:** Gemini 2.5 Flash + gemini-embedding-001 + Chirp + Document AI; AI.GENERATE, ML.GENERATE_TEXT, ML.GENERATE_EMBEDDING + VECTOR_SEARCH (no index mentioned), ML.TRANSCRIBE, ML.PROCESS_DOCUMENT, AI.FORECAST; Object Tables over audio and PDFs (multimodal Y); deployed live app Y; chat assistant but no tool-calling agent described; BigFrames N; public dataset N.

### 5. ReDrugAI (Vector Search 2nd, $9k, team ReDrugAI)
Authors: Ting-Wei Chu, catvin_hsiao (Hung Yu Hsiao), plus consultant Zi-Ting Feng (PhD ChemE). Links: [GitHub catmei/ReDrugAI](https://github.com/catmei/ReDrugAI) ([main.ipynb](https://github.com/catmei/ReDrugAI/blob/main/main.ipynb)), [Medium](https://medium.com/@quantcat666/redrugai-repurposing-existing-drugs-as-new-treatments-with-google-bigquery-ai-ae0e5c256516). No video linked. Not in the bank beyond the judges' line.

**Problem and user.** Pharma / biomedical researchers looking for repurposing candidates: approved drugs with known safety that might treat another disease, especially rare diseases with few known treatments.

**Data.** **Open Targets Platform, BigQuery public dataset version** (drugs, targets, diseases, mechanism of action (MoA), known_drug associations).

**Method.** (1) Disease names + synonyms + descriptions concatenated and embedded with **`text-embedding-005`** ("embedding005", 768-d) via `ML.GENERATE_EMBEDDING`, pre-computed and stored behind a **BigQuery vector index**; `VECTOR_SEARCH` keeps diseases within cosine distance 0.3 of the target. (2) MoA descriptions also embedded; a table of pre-computed MoA-pair cosine similarities. (3) Candidate scoring: base = max MoA similarity to known treatments (0 to 1), times a tiered multiplier: x1.0 MoA only, x2.0 shared binding target (`target_id`), x5.0 exact MoA + target pair. (4) Dual score: `final = primary_disease_score + 0.5 x mean(similar_disease_scores)`. (5) Three outputs: known drugs (baseline), overall novel candidates (top 10, excluding approved), similar-disease recommendations (top 5). Fallbacks: if the target disease has no known drugs, aggregated patterns from similar diseases act as primary; if neither exists, return empty.

**Evaluation (strongest of the 11).** Leave-one-out style test on **100 randomly sampled diseases**: hide the known drugs, recommend, check exact drug-ID overlap with Open Targets `known_drug`. Recall: overall top-10 **21.55%**, similar-disease top-5 **23.90%**, combined **45.44%** (writeup). Precision and F1 computed but not reported in the text. The team argues the 54.56% non-matching recommendations are candidates, not failures (an interpretive claim, not validated).

**Generative AI use.** The abstract says the tool leverages BigQuery's generative AI, but no `AI.GENERATE` / `ML.GENERATE_TEXT` step is described in the writeup body (UNVERIFIED; check the notebook).

**Judges:** "used vector search to help research drug discovery with similarity matching ... clearly states the impact ... reducing the costs associated with drug discovery" ([612730](https://www.kaggle.com/competitions/bigquery-ai-hackathon/discussion/612730)).

**Matrix facts:** text-embedding-005; ML.GENERATE_EMBEDDING + VECTOR_SEARCH + vector index Y; AI.GENERATE ?; no multimodal; public dataset Y (Open Targets); BigFrames not mentioned; benchmark-with-baseline eval (components vs combined).

### 6. Causal RAG (Vector Search 3rd, $6k, laoyu84)
Links: [GitHub Laoyu84/bq_causal_rag](https://github.com/Laoyu84/bq_causal_rag), [video](https://youtu.be/C3GfcaQYhoo). Not in the bank beyond the judges' line.

**Problem and user.** Financial analysts asking 10-K questions that plain RAG fails: "why" questions (drivers of Salesforce's FY2025 net-margin rise) and non-obvious "what" questions (biggest anomaly in the FY21 income statement), plus calculations across many years that are too costly to stuff into a long context.

**Data.** Salesforce 10-K reports FY2018 to FY2025, chunked and embedded in BigQuery; a hand-built "approximation" per statement set (income_statement, balance_sheet): a causal graph among accounting variables (net income, revenue, costs ...) grounded in accounting identities, "sentiments" between variables expressed as accounting formulas, and a CSV of the statement figures 2018 to 2025. Built once, offline.

**Agent design (analyst / consultant pattern), all on Gemini 2.5 Flash via BigQuery:** (1) `ML.GENERATE_TEXT` extracts company and year from the query and classifies intent; (2) **Code-gen**: prompt with causal graph + sentiments + data schema/sample asks Flash to write Python that prints facts only ("DO NOT get to conclusions ... DO NOT make up any data"); the code runs locally and returns facts via stdout; no ReAct loop, the whole program is regenerated on failure; (3) Flash as "consultant" turns facts into insights; (4) **SQL-gen**: `ML.GENERATE_TEXT` writes a `VECTOR_SEARCH` query (top_k 5, COSINE) that pre-filters the chunk-embedding table by company_name and report_year, retrieving evidence chunks; final answer = insights + evidence. Choice of Flash over Pro is deliberate (cost; coding strength).

**Evaluation.** A small hand-built test set in two categories (basic fact/calculation; drivers/trend analysis), comparing **baseline BigQuery vector-search RAG**, **Gemini 2.5 Pro with thinking**, and Causal RAG. Results shown only as a figure; text claims Causal RAG "greatly outperforms" baseline RAG and matches Pro while being more stable, since Pro returned internal errors when fed eight annual reports at once. Set size and scores not stated in text (UNVERIFIED). Impact claims (baseline RAG fails ~30% of numeric tasks; $10 to 15M/yr productivity per Fortune 500 finance team) are the author's estimates.

**Judges:** "uses ML.GENERATE_TEXT to augment the SQL for the vector search code" ([612730](https://www.kaggle.com/competitions/bigquery-ai-hackathon/discussion/612730)).

**Matrix facts:** Gemini 2.5 Flash (+ embedding model unnamed); ML.GENERATE_TEXT, ML.GENERATE_EMBEDDING + VECTOR_SEARCH (no index mentioned); agentic Y (code-gen + SQL-gen, local code execution); no multimodal; data = public 10-K filings (not a BQ public dataset); BigFrames not mentioned; eval = small quantitative with two baselines.

### 7. OncOmix AI (Multimodal 1st, $15k, team MASHUP)
Authors: mayakalyan, Sharath Rathinakumar. Links: [Kaggle notebook](https://www.kaggle.com/code/mayakalyan/oncomix-ai) (kernels/pull returned an empty source, so not read), [video](https://youtu.be/VzOfrgzVV80), [GitHub](https://github.com/sharath6umich/OncOmix-AI-BigQuery.git), [Medium](https://medium.com/@mayakalyan08/oncomix-ai-bigquery-powered-multimodal-insights-for-personalized-oncology-research-and-care-d579b849ec9b). Bank covers the RAG design; additions below.

**Problem and user.** Translational-oncology clinicians, tumour boards and researchers who must connect a patient's multi-omic profile to a fast-moving PubMed literature, and who distrust ungrounded "black box" AI.

**Data.** Public: **TCGA breast cancer cohort of 500 patients** (clinical, RNA expression, mutation, CNV, protein, methylation, treatment) plus "thousands" of PubMed breast-cancer abstracts, cleaned and joined with **BigFrames** (BigFrames Multimodal DataFrame). "Multimodal" here means structured omics + unstructured text, not images or audio.

**Pipeline.** Abstracts embedded with BigFrames **`TextEmbeddingGenerator`** (`ML.GENERATE_EMBEDDING` underneath) into BigQuery; per-patient queries built from the profile ("breast cancer, ER positive, HER2 negative, PIK3CA mutation") run through `VECTOR_SEARCH`; retrieved abstracts tagged by similarity (>= 75% strong, 60 to 74% moderate); **`bigframes.ml.llm.GeminiTextGenerator`** writes structured patient summaries (context, multi-omic signals, mechanism, predicted outlook, follow-ups, verbatim cited evidence). Research arm: a **Literature Validation Score (LVS)** combining cohort biomarker signal (frequency, impact) with literature footprint (count and relevance of retrieved PMIDs) to separate "ready now" biomarkers (ERBB2, ESR1, BRCA1/2) from watch-list (TP53, MAP3K1, PTEN) and under-explored ones (CD274/PD-L1, LAG3, CTLA4); Gemini also writes cohort insights; demographic and subtype-by-age plots. Gemini and embedding model versions are not named in the writeup (UNVERIFIED).

**Evaluation.** None quantitative: three illustrative patient summaries (e.g. TCGA-A8-A09N) in `summaries.csv`, and the observation that the cohort reproduces known breast-cancer patterns (Luminal A older, basal-like/TNBC younger). Explicit "research prototype, not for clinical use" disclaimer; the authors caveat that the immune-checkpoint "gap" may be an artefact of their limited literature slice.

**Judges:** "uses BigQuery multimodal functionality to produce insights for oncology ... explains the problem statement and how using AI can aid and assist in the research" ([612730](https://www.kaggle.com/competitions/bigquery-ai-hackathon/discussion/612730)). Claims to use all three approaches.

**Matrix facts:** Gemini (version ?), BigFrames GeminiTextGenerator + TextEmbeddingGenerator; AI.GENERATE family via BigFrames Y; ML.GENERATE_EMBEDDING + VECTOR_SEARCH Y (index ?); ObjectRef / Object Tables N (multimodal = mixed structured + text); BigFrames Y; public data Y (TCGA, PubMed; whether via BigQuery public datasets is not stated); no agent.

### 8. Grid Incident RAG (Multimodal 2nd, $9k, seyyedreza madani / Reza Madani)
Links: [GitHub srmadani/Grid-Incident-Rag](https://github.com/srmadani/Grid-Incident-Rag), [Medium](https://medium.com/@seyyedreza.madani/turning-153-wildfire-pdfs-into-answers-a-sql-only-rag-system-88ca9982a5fe), source [CPUC wildfire staff investigations](https://www.cpuc.ca.gov/industries-and-topics/wildfires/wildfires-staff-investigations), public bucket `gs://grid-incident-rag-docs/`. No video linked in the writeup (Streamlit screenshots instead). Not in the bank beyond the judges' line.

**Problem and user.** Utility engineers and regulators who need cross-incident patterns (which equipment fails, under what weather, where) buried in 153 California Public Utilities Commission wildfire incident reports of 20 to 200 pages each (3,000+ pages).

**Data.** Public CPUC PDFs mirrored to a public GCS bucket. Document AI Layout Parser parsed 130 of 153 PDFs (85%), producing 3,334 chunks (3,229 embedded per the cost table; the writeup gives both numbers).

**Pipeline, "everything in SQL":** Object Table over the PDFs; `ML.PROCESS_DOCUMENT`-style Document AI Layout Parser (tables, multi-column, reading order); `ML.GENERATE_EMBEDDING` with **textembedding-gecko** (768-d) per chunk; `VECTOR_SEARCH` with metadata pre-filters (utility, year, fire-threat tier; claims up to 93% search-space reduction); RAG answer through `ML.GENERATE_TEXT` with citations and a similarity-based confidence; **`AI.GENERATE_TABLE` with dynamic schema** extracted 126 incident records with 40+ fields into six tables (incident core, impact, equipment failures, vegetation, regulatory violations, investigation). BigQuery ML **K-Means** gives four risk profiles for a "risk predictor". Streamlit app: dashboard, incident explorer, pattern analyzer, compliance monitor, chat, eval report, cost page. Generation model name not stated (UNVERIFIED).

**Lesson reported.** Mixing embedding models with identical dimensions produced "nonsensical results"; use one embedding model end to end. Adding 20% chunk overlap and filtering low-quality chunks raised citation recall by 33% (writeup).

**Evaluation (one of the most rigorous here).** LLM-as-judge over **358 auto-generated questions** from the extracted structured data: correctness **3.76/5**, faithfulness **100%**, citation recall **58.9%** (writeup). No external baseline system. Cost accounting: whole project **$39.57** (Document AI $32.50 for 2,600 pages, embeddings $0.10, eval $1.34), ~$0.004 per query. Findings surfaced: conductors in 67% of equipment failures, October 3x average, GO 95 violations in 89% of incidents, mean equipment age at failure 23 years.

**Judges:** "uses past historical multimodal data to search and summarize patterns in previous incidents ... impact on both cost and time" ([612730](https://www.kaggle.com/competitions/bigquery-ai-hackathon/discussion/612730)).

### 9. Auto-Updating Documentation with BigQuery AI (Multimodal 3rd, $6k, Illya Moskvin + Jacob Bridges)
Links: [GitHub jacobbridges/kaggle-bigquery-ai-2025-public](https://github.com/jacobbridges/kaggle-bigquery-ai-2025-public), [video](https://www.youtube.com/watch?v=qNa2ULGu_PE), public BigQuery dataset `tensile-reducer-471101-f0.public` (stated to be removed after the competition). Not in the bank beyond the judges' line.

**Note on category.** The writeup opens "We are targeting the 'Best in Generative AI' (AI Architect) track"; the judges placed it **3rd in Multimodal**. Its only BigQuery AI call is `AI.GENERATE`; the multimodal element is Object Tables over heterogeneous files (Markdown docs, Slack JSON, Zoom WebVTT, change requests, PR summaries, prompts).

**Problem and user.** Engineering teams suffering "documentation divergence", split into implementation drift, source fragmentation and "decision amnesia" (decisions made in chat never reach the docs). Fix by looking at changes over time: take the last verified doc + its timestamp, collect ephemera created since, generate a new version, send it for human review, commit, repeat.

**Data.** A toy to-do-app project; part of the sample data was generated with **Claude Sonnet 4**. Ephemera and docs live in GCS with custom object metadata (`timestamp`, `ephemera_type`, document type).

**Design, built up in four tutorial stages:** (1) PoC: one spec + one Slack conversation through `AI.GENERATE` with endpoint **`gemini-2.0-flash-lite`**, `output_schema => 'result STRING'`, and a fixed **seed (12345)** for run-to-run consistency; (2) many ephemera: SQL CTEs pick the latest document and only ephemera newer than it (a pre-dated conversation must be ignored, small talk filtered), prompt primed to capture decisions and preserve structure; (3) multiple ephemera types: prompts stored as GCS objects in their own Object Table and joined by `ephemera_type` (`slack_json`, `zoom_vtt`, `change_request`), since a change request "is the decision" while chat needs consensus extraction; (4) multiple document types: prescriptive "specs" vs descriptive "docs", with a prompt per (document type, ephemera type) pair (e.g. `documentation^slack_json.md`), so chat changes specs but only PR summaries change docs. Shown result: a doc diff replacing `status` with `complete` per a Slack decision. One document updated per query to control cost.

**Evaluation.** Qualitative only: worked examples and diffs; no metric or baseline. Recommendations: keep the human in the loop, use docs-as-code review tools, feed outputs of specialised agents (Copilot PR summaries, Zoom AI Companion) rather than raw ephemera; future work on citations (`source_url` footnotes) and reconciling contradictory docs.

**Judges:** "uses various multimodal datapoints to help auto generate documentation ... explains why the problem is magnified and how their solution mitigates the issue" ([612730](https://www.kaggle.com/competitions/bigquery-ai-hackathon/discussion/612730)).

**Matrix facts:** gemini-2.0-flash-lite; AI.GENERATE only (no GENERATE_TABLE, no embeddings / VECTOR_SEARCH); Object Tables Y (ObjectRef not used); BigFrames N; own toy data partly LLM-generated; published its own public BQ dataset; no agent.

### 10. Patent Intelligence: Semantic Search for Innovation Discovery (Honorable Mention, $5k, sl02 / laxmsun)
Links: [Kaggle notebook](https://www.kaggle.com/code/laxmsun/patent-intelligence-semantic-search-for-innovatio?scriptVersionId=262939955), [Streamlit demo](https://patent-art.streamlit.app), [GitHub sl2902/patent_art](https://github.com/sl2902/patent_art), [Medium](https://medium.com/@laxmsun_33290/patent-intelligence-semantic-search-for-innovation-discovery-bd526f3891d1), [survey dataset](https://www.kaggle.com/datasets/laxmsun/bigquery-ai-survey). No video linked. Not in the bank.

**Problem and user.** Prior-art and competitive-intelligence researchers for whom keyword patent search misses conceptually related inventions (WIPO: 3.6M applications in 2023).

**Data (biggest scale of the 11).** BigQuery public **Google Patents `publications`** table: 2.6 TB raw, 49,184,081 patents across 59 countries profiled (9 dashboard charts: China 71% of publications, US 12%; US citation rate 72% vs China 36%; claims completeness 12.1%); filtered to **2.9M English patents from Jan to Jun 2024 (14.4 GB)**, dropping titles under 30 chars and abstracts under 100. Table partitioned by month, clustered by `publication_id`, `country_code`.

**Embedding choice, against the grain.** The author first used `ML.GENERATE_EMBEDDING` on a 5.7M-row 2013-14 subset and found it too slow: 7 to 70 minutes per 5,000-row batch, 48K rows (one day) in 6 hours, ~0.45 s per embedding, i.e. ~15 days for 2.9M; also a LIMIT/OFFSET-without-ORDER-BY duplication bug fixed with ROW_NUMBER(). Switched to **SentenceTransformers `all-MiniLM-L6-v2` on a Kaggle GPU: 2.9M embeddings in 6.5 h** in 5,000-row batches ("56x faster"). BigQuery AI is then used for **`VECTOR_SEARCH`** only. A full vector index was built, but the author found index *use* requires Enterprise+ edition (Standard edition falls back to brute force) and reports this as a friction point. Query embeddings on CPU (~50 ms cloud, ~500 ms laptop). Features: text query or patent-number mode (multiple patents averaged), relevance bands (>65% high, 50 to 65% moderate), and sentence-level explainability (top 3 query/patent sentence pairs).

**Evaluation.** Systems metrics on 10 queries: vector search mean 3.0 s on Kaggle (p90 3.2 s) vs 4.5 s laptop; full pipeline with explainability 5.2 s vs 12.9 s; 1-month partition pruning cut bytes processed 84% and latency 12%. Semantic vs keyword on 10 queries: semantic returned 300 results, keyword 180, overlap only 5, reported as "98.3% unique". The author explicitly states relevance, recall and precision **cannot** be measured without ground truth, so this is a discovery-overlap measure, not a quality measure.

**Judges:** "used vector search functionality ... identifying similarities or lack thereof for ideas vs patents ... how the savings translate to digestible summarizations and the time costs of each" ([612730](https://www.kaggle.com/competitions/bigquery-ai-hackathon/discussion/612730)).

**Matrix facts:** all-MiniLM-L6-v2 (external, offline), no Gemini generation in the writeup; VECTOR_SEARCH Y, vector index built but unusable on Standard edition; ML.GENERATE_EMBEDDING tried and abandoned (queries embedded outside BQ); AI.GENERATE N; multimodal N; BigFrames N; BQ public dataset Y; live demo Y.

### 11. CLARIS: County-Level Augmented Risk Intelligence System (Honorable Mention, $5k, Tiyab K.)
Links: [Kaggle notebook](https://www.kaggle.com/code/tiyabk/county-level-augmented-risk-intelligence-system) (pulled for model names), Substack posts [1](https://ktiyab.substack.com/p/pattern-matching-at-scale-with-bigquerys) [2](https://ktiyab.substack.com/p/pattern-matching-at-scale-with-bigquerys-617). No video or GitHub linked in the writeup. Bank gives one line only.

**Writeup quality caveat.** The writeup is long but generic: large parts paraphrase BigQuery documentation (what an embedding is, IVF/ScaNN indexes, brute force under 5,000 rows) and it contains no concrete results, query outputs, or sample counts. Specifics below come mostly from the notebook.

**Problem and user.** Mid-market property and casualty insurers' underwriting, monitoring and reinsurance teams: actuarial models ignore the qualitative signals in preliminary weather reports and eyewitness comments.

**Data.** Two **NOAA severe-weather datasets available in BigQuery**: the historical storms database (Jan 1950 to Apr 2025, verified events with damage and casualties; `noaa_historic_severe_storms`) and preliminary storm reports (hail, tornado, wind, including social-media comments). Aggregated into three tables: `historical_risk_master` (county-month, FIPS-coded, rolling stats), `event_reports_master` (last-30-day reports), `enriched_location_master` (75-year county baselines + current activity). The notebook runs generation on a **100-row sample** (`SAMPLE_SIZE = 100`).

**BigQuery AI use:** remote models `gemini-2.5-flash` and `gemini-embedding-001` (notebook; the writeup itself cites gemini-2.0-flash only as a docs example). `ML.GENERATE_TEXT` with three prompt types (underwriting, monitoring, comparative) writes county risk narratives / hypotheses; **`AI.GENERATE_BOOL`** gives three routed alerts (abnormal 30-day activity vs 75-year average, customer notification, worsening 5-year trend), with a prompt trick of counting digits to judge damage magnitude (10 digits = billions) and explicit FALSE conditions to avoid alert fatigue; `AI.GENERATE_TABLE` maps narratives to a structured risk-classification schema with confidence; `ML.GENERATE_EMBEDDING` creates county "risk fingerprints" and event embeddings; `VECTOR_SEARCH` finds analogous counties / scenarios. All outputs labelled "PRELIMINARY" for human validation.

**Evaluation.** None. Benefits ("weeks to hours", 100% vs <10% of reports reviewed, 30 to 60 days earlier warning) are asserted without measurement.

**Judges:** "uses AI.GENERATE functions such as AI.GENERATE_BOOL to classify the level of risk based on historical weather data for insurance ... a clear actionable goal and a measurable impact" ([612730](https://www.kaggle.com/competitions/bigquery-ai-hackathon/discussion/612730)).

**Matrix facts:** gemini-2.5-flash + gemini-embedding-001; ML.GENERATE_TEXT, AI.GENERATE_BOOL, AI.GENERATE_TABLE, ML.GENERATE_EMBEDDING + VECTOR_SEARCH (index discussed, not shown created); multimodal N; BigFrames N; BQ public dataset Y (NOAA); no agent; no video.

## Consensus vs divergence

**Table stakes (nearly all winners).** Public GitHub or notebook (11/11) plus an architecture diagram, matching the 20% "assets" and 10% "architecture" rubric lines; a quantified business impact (hours, dollars, ROI) in every writeup, which every judges' note mentions; the whole pipeline kept inside BigQuery SQL (remote Gemini models, Object Tables, VECTOR_SEARCH) rather than calling Gemini from Python; multi-function use (most winners combine 3 or more BigQuery AI functions, crossing category boundaries).

**What separated the 1st places.** The three category winners are the broadest builds: TriLink (5 workflows, 6+ BigQuery AI functions, BQML, an ADK agent), SpeakAura (deployed app, audio pipeline, 6 functions), OncOmix (claims all three approaches). Breadth of BigQuery AI use and a convincing real-world user story mattered more than measured accuracy: none of the three 1st places reports a quality metric, while the two most rigorous evaluations (ReDrugAI's leave-one-out recall, Grid RAG's 358-question LLM-judge) placed 2nd. The honorable mentions are the narrowest in BigQuery AI use (PI uses VECTOR_SEARCH only with external embeddings; CL's writeup is mostly documentation paraphrase with no results).

**Contradictory choices.**
- *Native vs external embeddings:* most winners used `ML.GENERATE_EMBEDDING` (e.g. [ReDrugAI](https://www.kaggle.com/competitions/bigquery-ai-hackathon/writeups/redrugai0421), text-embedding-005 over Open Targets), while [Patent Intelligence](https://www.kaggle.com/competitions/bigquery-ai-hackathon/writeups/patent-intelligence-semantic-search-for-innovation) abandoned it as too slow at 2.9M rows (~15 days projected) and used MiniLM on a Kaggle GPU (6.5 h). Scale decides: the others embedded thousands of rows, not millions.
- *Vector index:* ReDrugAI stores embeddings behind a vector index; Patent Intelligence reports that index use needs Enterprise+ edition, so on Standard edition VECTOR_SEARCH is brute force anyway.
- *Free-text prompts vs structured functions:* [TriLink](https://www.kaggle.com/competitions/bigquery-ai-hackathon/writeups/trilink-architecting-the-ai-native-digital-service) deliberately used plain `AI.GENERATE` over `AI.GENERATE_TABLE` for coaching aggregation "for more control on the prompt design", while [Patent Analyst](https://www.kaggle.com/competitions/bigquery-ai-hackathon/writeups/the-ai-patent-analyst) and [ESG](https://www.kaggle.com/competitions/bigquery-ai-hackathon/writeups/new-writeup-1757758945521) built their core on `AI.GENERATE_TABLE` schemas.
- *Model size:* [Causal RAG](https://www.kaggle.com/competitions/bigquery-ai-hackathon/writeups/causal-rag) argues Flash + code generation matches Pro and is more stable on many 10-Ks; [ESG](https://www.kaggle.com/competitions/bigquery-ai-hackathon/writeups/new-writeup-1757758945521) chose Gemini 2.5 Pro for extraction.
- *Category self-selection:* Auto-Updating Docs targeted Generative AI but was placed in Multimodal; the judges evidently assigned categories themselves.
