> **TL;DR.** The NeurIPS 2025 Google Code Golf Championship (July 31 to October 30, 2025, 1,142 teams) asked for the shortest Python program that solves each of the 400 ARC-AGI-1 training tasks. A task scores 2,500 minus its byte count if it is right on every example and 0.001 if it is wrong anywhere. The podium went to three teams of human golfers: Code Golf International (962,070), jailctf merger (961,805) and ox jam! (961,784), all within 286 points. The strongest LLM-driven team, FuunAgent, finished 4th, 3,974 points behind 3rd, with code one member describes as 98% generated by gpt5-codex. All 14 top-20 teams with a source compressed their long solutions with zlib. **The lesson:** when the answer is checkable, an LLM loop gets you into the chasing pack cheaply; the last ten bytes per task still came from people who had golfed for years.

![Lever strip with Metric insight lit for Code Golf](/imgs/blogs/kaggle-google-code-golf-2025-solutions-1.webp)

The strip above is the series frame: five levers, one lit per competition. Code Golf is the odd one out. There is no model to fit, no retrieval, no notebook budget, and test-time compute is free because you run it at home. What decided the board was optimising the true objective, bytes after compression, and the people best at that were humans. It is the cleanest answer Kaggle has produced to "can an LLM do it?": yes, to 4th place, and this post shows where it stopped. ## The task in 60 seconds

ARC-AGI-1 is the abstraction benchmark behind the [ARC Prize 2024 post](/blog/machine-learning/learn-from-kaggle/kaggle-arc-prize-2024-solutions): a few input/output grid pairs, and you infer the rule. Code Golf flipped it. The 400 public training tasks were given, and extra examples for each came from ARC-GEN, a generator that produces new pairs following the task's rule. The job was not to discover rules but to write them down in as few bytes of Python as possible.

![Budget card: no Kaggle GPU, 400 stdlib-only files, score is bytes](/imgs/blogs/kaggle-google-code-golf-2025-solutions-2.webp)

The budget card has no GPU line. You submit 400 files, `task001.py` to `task400.py`, each defining `p(grid)` that returns the output grid, using only the standard library, each self-contained (security constraints went live on August 19). Every file must be right on the task's train, test and ARC-GEN pairs. The leaderboard was 100% public, with 100 submissions a day. Google DeepMind hosted it in the NeurIPS 2025 Competition Track; prizes were USD 30k, 20k and 10k, then 5k each for 4th to 10th, plus a 5k "Longest Leader" prize whose recipient we could not verify.

![Illustrative toy task: paint the outer frame of a 5 by 5 grid azure](/imgs/blogs/kaggle-google-code-golf-2025-solutions-3.webp)

The figure is an illustrative toy in the ARC style, not one of the 400 tasks: paint the outer frame colour 8 and leave the inside alone. Underneath is a 70-byte solution we golfed for this post. It looks like line noise; every character is doing work, and the techniques that produced it are the subject of the rest of this post.

## The metric, worked on four tasks

Let $b_t$ be the byte length of the file for task $t$. The score is a plain sum:

$$
S = \sum_{t=1}^{400} s_t, \qquad s_t = \begin{cases} \max(1,\ 2500 - b_t) & \text{if } p_t \text{ is right on every example} \\ 0.001 & \text{otherwise} \end{cases}
$$

Length is a linear ramp with slope minus one: one byte anywhere is one point, with no weighting by difficulty. Correctness is a cliff: a file that fails one ARC-GEN example scores the same as a file that does nothing.

![Points versus file size: a linear ramp with a floor at 1, and a cliff for wrong answers](/imgs/blogs/kaggle-google-code-golf-2025-solutions-4.webp)

Four toy tasks make it concrete. Task A is our 70-byte frame solution: 2,430. Task B is a long task shipped as a 202-byte compressed file: 2,298. Task C is a correct 2,600-byte brute force, past 2,499 bytes, so it hits the floor and scores 1. Task D is 300 bytes and wrong on one pair: 0.001. The total is 4,729.001. Solving all 400 at any length is the first milestone every writeup mentions; after that the game is bytes.

A useful way to read the final board is to invert it. If a team solved all 400, its average file is (1,000,000 minus score) divided by 400. The winner's 962,070 means about 94.8 bytes per task; 4th averaged about 105.5 and 20th about 123.3. The whole top 20 sits in a 28-byte-per-task band, and first and second are 265 points apart, two thirds of a byte per task.

## What made it hard

None of it was compute.

**The examples punished shortcuts.** ARC-GEN pairs exercise corners the original pairs never show: odd sizes, colours that only appear in generated cases, objects touching the border. A clever rule that fits the train pairs often breaks on a generated pair and falls off the cliff. The LLM teams paid most here.

**The field saturated early, in public.** The code.golf community arrived with years of Python idioms. Luke G of the eventual winner opened a thread for sharing per-task scores, and that spreadsheet became the benchmark everyone chased. Public notebooks with golfed solutions moved the board, enough that c-number asked in the final three days whether people could pause solution releases.

**The metric had holes.** Byte length was measured after running the submitted code, so monkey-patching `os.path.getsize` posted impossible scores in the billions. Another method worth 960K+ was reported privately (by isakatsuyoshi, later of 15th) and patched on August 25. Shelling out through `os.popen` was ruled legal late; the top three agreed not to use it, per the 1st-place writeup. Measure after untrusted code finishes, not while it runs.

| Question | One side | Other side |
|---|---|---|
| Are LLMs worth it? | 8th: leaning on LLMs "was not going to get us anywhere near the top" | 7th built its whole workflow on Codex and finished one place higher |

## The winning solution: Code Golf International

Five experienced golfers (Luke G, Mukundan, Seek64, 4atj, sisyphus-cg) wrote all 400 solutions by hand: a few hours per task per author, plus reviewers, with many tasks revisited when a new trick appeared. The only automation was compression, on 21 tasks. No LLMs. The writeup is a catalogue of idioms, and the best Python golf reference I know of.

### The recursion template

The basic vocabulary leans on sequence tricks: `zip(*g)` transposes, `g[::-1]` mirrors, `zip(*g[::-1])` rotates, `filter(any,g)` drops empty rows, `{}.fromkeys(r)` gives a row's colours in order. Many ARC rules are "do something to one side, then the other three", so rotation is the workhorse, and the most reused pattern applies a step $F$ with rotation baked in:

```python
p=lambda g,n=3:-n*g or F(p(g,n-1))
```

The trick is `-n*g`. A list times zero or a negative number is empty and falsy, so for n equal to 3, 2, 1 and 0 the `or` falls through to the recursive call. At n equal to minus one, `-n*g` is the grid itself, truthy, and recursion stops. No `if`, no base-case keyword. The winners extended it to depth-two variants, loop forms like `[g:=F(g)for _ in g][3]`, and "slice recursion" such as `p=lambda g:F(g[70:]or p(g*2))`; task 093's `g[57330:]` works because 57,330 is 14 times (2 to the 12th, minus 1), so a 14-row grid doubles exactly 12 times before the slice is non-empty.

Here is the template on the frame task, inside a ladder that shows where the bytes go.

```python
# Illustrative toy, not any team's code. Task: paint the outer frame of a
# square grid colour 8. Four solutions, scored with the competition formula.
import random

def frame(g):                                   # reference answer
    n = len(g)
    return [[8 if {i, j} & {0, n - 1} else g[i][j] for j in range(n)]
            for i in range(n)]

random.seed(0)
tests = []
for n in (3, 4, 5, 7):
    g = [[random.choice([0, 0, 1, 2]) for _ in range(n)] for _ in range(n)]
    tests.append((g, frame(g)))

readable = """def p(grid):
    n = len(grid)
    out = []
    for i in range(n):
        row = []
        for j in range(n):
            if i == 0 or j == 0 or i == n - 1 or j == n - 1:
                row.append(8)
            else:
                row.append(grid[i][j])
        out.append(row)
    return out
"""
ladder = [
    ("readable def", readable),
    ("one comprehension", "def p(g):n=len(g);return[[8 if{i,j}&{0,n-1}else g[i][j]for j in range(n)]for i in range(n)]"),
    ("rotate, recurse x4", "p=lambda g,n=3:-n*g or[[8]*len(g)]+[*map(list,zip(*p(g,n-1)[::-1]))][1:]"),
    ("transpose + slice", "p=lambda g,n=3:-n*g or[[8]*len(g)]+[*map(list,zip(*p(g,n-1)))][-2::-1]"),
]
for name, src in ladder:
    env = {}
    exec(src, env)
    ok = all(env["p"]([r[:] for r in i]) == o for i, o in tests)
    b = len(src.encode())
    print(f"{name:19} {b:4} bytes  correct={ok}  points={max(1, 2500 - b) if ok else 0.001}")
```

Run with `python3 -I`:

```console
readable def         298 bytes  correct=True  points=2202
one comprehension     91 bytes  correct=True  points=2409
rotate, recurse x4    72 bytes  correct=True  points=2428
transpose + slice     70 bytes  correct=True  points=2430
```

![Byte ladder for the toy frame task, from 298 bytes to 70](/imgs/blogs/kaggle-google-code-golf-2025-solutions-8.webp)

The step that matters is the third. Instead of asking "is this cell on the border?" per cell, the recursive version paints the top row, rotates, and repeats; after four rotations the grid is back in place with all four sides painted. The last two bytes come from noticing that a transpose plus the reversed slice `[-2::-1]` is a counterclockwise rotation that also drops the old top row, so one slice does the job of `[::-1]` and `[1:]`. That is what hours per task buy: a reformulation in which the language does more of the work. The chart's 202-byte bar is the readable version compressed, covered below.

### Regex on the printed grid

Forty-six of the winner's solutions turn the grid into a string, rewrite it with a regular expression, and `eval` it back. `str(g)` lays the grid out regularly: one digit and `, ` per cell, brackets per row, so the cell directly below another is always the same distance away, ${3w+2}$ characters on a grid of width $w$. A lookbehind `(?<=5.{34})` therefore means "a 5 directly above me" on an 11-wide grid, the gap task 294 uses: `p=lambda g:eval(re.sub("(?<=5.{34})5(?=.{34}5)","2",str(g)))`.

```python
# Illustrative toy, not any team's code: regex over str(g), then eval.
import re
# Task A: a 0 with a 5 on its left and right becomes 2.
A = 'import re;p=lambda g:eval(re.sub("(?<=5, )0(?=, 5)","2",str(g)))'
# Task B: same, but vertically, on 5-wide grids. One row down = 3*5+2 = 17
# characters of str(g), so 16 characters sit between a cell and the one below.
B = 'import re;p=lambda g:eval(re.sub("(?<=5.{16})0(?=.{16}5)","2",str(g)))'
gA = [[5,0,5,0,0],[0,5,0,5,5]]
gB = [[0,5,0,0,0],[0,0,0,5,0],[0,5,0,0,0]]
for name, src, g in (("A", A, gA), ("B", B, gB)):
    env = {}; exec(src, env)
    print(name, len(src.encode()), "bytes ->", env["p"](g))
print(repr(str([[1,2],[3,4]])))
```

```console
A 64 bytes -> [[5, 2, 5, 0, 0], [0, 5, 2, 5, 5]]
B 70 bytes -> [[0, 5, 0, 0, 0], [0, 2, 0, 5, 0], [0, 5, 0, 0, 0]]
'[[1, 2], [3, 4]]'
```

The lookbehind in Task A requires `5, ` with the comma, so a 5 ending one row cannot leak into the next, which starts after `], [`. The winners went further: rotate-and-replace loops apply one regex in all four directions, and a replacement `*[\g<0>][::-1]` reverses a match in place. Other ideas from the same writeup: "dimension recursion", where one `p` handles grid, row and cell by branching on `g*0!=0`; guess-and-check (task 124); and brute-forced hash lookup tables for special cases.

### Compression, done properly

For long tasks, the file is a compressed blob plus a stub that decompresses and runs it. The toy below continues the block above.

```python
# Illustrative toy, continues the block above: wrap code in a raw-deflate
# stub, write it to disk, run it, and compare sizes.
import os, runpy, tempfile, zlib

def pack(src):
    z = zlib.compressobj(9, zlib.DEFLATED, -9)   # raw deflate, no header/checksum
    data = z.compress(src.encode()) + z.flush()
    esc = {0: b"\\0", 10: b"\\n", 13: b"\\r", 39: b"\\'", 92: b"\\\\"}
    body = b"".join(esc.get(c, bytes([c])) for c in data)
    return b"#coding:L1\nimport zlib\nexec(zlib.decompress(bytes('" + body + b"','L1'),-9))"

for name, src in (ladder[0], ladder[3]):
    path = os.path.join(tempfile.mkdtemp(), "task.py")
    open(path, "wb").write(pack(src))
    p = runpy.run_path(path)["p"]
    ok = all(p([r[:] for r in i]) == o for i, o in tests)
    print(f"{name:19} raw {len(src.encode()):3} B -> packed {os.path.getsize(path):3} B  correct={ok}")
```

```console
readable def        raw 298 B -> packed 202 B  correct=True
transpose + slice   raw  70 B -> packed 136 B  correct=True
```

The stub costs 63 bytes before any payload, plus a byte for each compressed byte that must be escaped in the literal. `#coding:L1` is the shortest legal encoding line, and Latin-1 maps every byte to one character, so the stream sits in the source almost verbatim. Negative `wbits` selects raw deflate, dropping a 6-byte header and checksum for a 4-byte `,-9`. Compression rescues verbose code (298 to 202) but nearly doubles a golfed 70-byte file, which is why teams compressed only past roughly 200 to 240 bytes.

The winner went well past zlib: a first pass from zopfli or libdeflate, then a re-encoder that keeps the Huffman tree and uses dynamic programming to account for each byte's escape cost inside a Python literal, plus a search over variable names. Their headline insight: **under compression, repetition is nearly free, so write repetitive code.** A golfer factors out a repeated fragment; deflate prefers it repeated, because a back-reference costs less than the factoring.

## Second and third place

### 2nd: jailctf merger, the fuzzer team

Five CTF players; lydxn, a seasoned golfer, did most of the golfing. Their signature tool is **charbrute**, a character-level fuzzer making random deletions, insertions and substitutions around a hotspot, plus a chunk mover, run on PyPy 3.11. Most saves were small, some large, and it found 100+ bytes in the final stretch. A fuzzer suits golf because fitness is free: run the tests, count the bytes. They invested early in compression: header and checksum stripped with `wbits=-9`, and a variable-rename GA that, in their words, was "implemented by gemini". They ended with 24 compressed tasks.

Their LLM account is the most candid in the competition. For long tasks, an LLM wrote a first working solution from the ARC-GEN generator code, golf tips and human hints; humans then golfed it. Verdict: "Most of the llm solutions we golfed got obsoleted by either public notebooks or with a solution rewrite." The LLM bought a correct 0 to 1; it did not survive to the final file.

### 3rd: ox jam!, the veterans

The team (per the README: ovs, xsot, JoKing, att/zacjl, MeWhenI) worked by hand. A `merge_and_submit.py` takes each member's best per task and applies zlib. They credit pysearch, Lynn's brute-force search for short Python expressions, and garrymoss's public notebook; no LLM use is mentioned. JoKing had predicted in the forum that LLMs would miss exactly what veterans rely on: bitwise tricks, pysearch formulas, regex and recursion. The final board agreed.

## 4th place: FuunAgent, the best LLM-driven entry

![FuunAgent loop: fresh sandbox, gpt5-codex, four samples, verify, keep shortest, AST-written next prompt](/imgs/blogs/kaggle-google-code-golf-2025-solutions-7.webp)

FuunAgent (Kohei, Jokrasa, THUNDER THUNDER) is why this competition matters to anyone building coding agents. One member's solutions were "98% generated by an LLM and only about 2% by human effort". The loop is a textbook [agent loop](/blog/machine-learning/ai-agent/agent-loop-anatomy) with an exact verifier in the middle.

1. **A session per task.** gpt5-codex with tools analyses the task JSON in a REPL, for 10 to 30 turns.
2. **Best of four.** Each turn generates four versions in parallel, evaluates them, and keeps the shortest valid one: [test-time compute](/blog/machine-learning/scaling-laws/test-time-compute-scaling) in its simplest form, where the verifier is exact so more samples only help.
3. **Prompts written by rules over the AST.** No regex in the current best, so "Try to use the regex re package"; a loop, so suggest recursion; a `def`, so suggest a lambda. The base prompt was "Please make it as short as possible in bytes for Code Golf and tell me the file size", and "Shorter code is known to exist." kept the model trying.
4. **Stopping and exploring.** Stop after $s$ turns without gain; after $t$ such turns, $t$ smaller than $s$, switch to exploration prompts like "Analyze the test cases generation code." and "Rethink a more compact algorithm."
5. **Fresh sandboxes.** A repository holding old solutions anchored the model; an empty sandbox per session broke those local optima.

The member ran about 15 Codex Cloud sessions in parallel on a ChatGPT Pro subscription, by hand from a phone, for three months, later moving to `codex exec` in Docker with SQLite logs. In the last two weeks the objective became size after compression. Grok-4 was tried and dropped for tool misuse and cost, and human teammates broke stalls. Here is a toy of one turn.

```python
# Illustrative toy, not any team's code: one turn of a "sample N, verify,
# keep the shortest, critique from the AST" loop. The four candidates stand
# in for four parallel LLM samples.
import ast
tests = [([[1,0],[2,3]], [[0,1],[3,2]]), ([[4,5,6]], [[6,5,4]])]
class Liar(list):                       # the "hack" a model may emit
    def __eq__(self, other): return True
samples = [
    "def p(g):\n return[r[::-1]for r in g]",
    "p=lambda g:[r[::-1]for r in g]",
    "p=lambda g:[r[::1]for r in g]",                 # shorter? no: wrong
    "p=lambda g:Liar()",                             # passes == locally
]
def valid(src):
    env = {"Liar": Liar}
    try:
        exec(src, env)
        outs = [env["p"]([r[:] for r in i]) for i, _ in tests]
    except Exception:
        return False
    plain = all(type(o) is list and all(type(r) is list for r in o) for o in outs)
    return plain and all(o == t for o, (_, t) in zip(outs, tests))
def critique(src):
    tree = ast.parse(src); hints = []
    if any(isinstance(n, ast.FunctionDef) for n in ast.walk(tree)): hints.append("Use a lambda, not def.")
    if any(isinstance(n, (ast.For, ast.While)) for n in ast.walk(tree)): hints.append("Replace the loop with recursion.")
    if "re." not in src: hints.append("Try the re package on str(g).")
    return hints + ["Make it as short as possible in bytes. Shorter code is known to exist."]
for s in samples:
    print(f"{len(s):3} bytes  valid={valid(s)}  {s!r}")
best = min((s for s in samples if valid(s)), key=len)
print("kept:", repr(best))
print("next prompt:", " ".join(critique(best)))
```

 17 bytes  valid=False  'p=lambda g:Liar()'
kept: 'p=lambda g:[r[::-1]for r in g]'

The `Liar` candidate is not hypothetical: 15th built a hack filter after models produced objects whose `__eq__` always returns true, which pass a naive local check and fail on the server. [Validate the output's type](/blog/machine-learning/ai-agent/agent-output-validation), not just its equality.

Why did the loop stop at 4th? The writeups of 7th, 8th, 15th and 19th agree from different angles: LLMs golf well once the direction is set and struggle to change it. Ten bytes per task is mostly direction: the recursion that replaces a loop, the regex that replaces a scan, the slice that does two jobs.

## Ranks 5 to 20, by approach family

### Hand golf from competitive programmers (5th, 6th, 9th)

**HIMAGINE THE FUTURE. (5th)**, a student CP/CTF team new to golf and Kaggle, split effort as "90% grinding code golf, 9% tooling, and 1% weird hacks". Their deflate optimiser beat Zopfli by about 700 points over native zlib: hill climbing removed characters needing escapes, and with the factorisation fixed, optimal Huffman code lengths fall out of a dynamic programme (one example: Zopfli 218 bytes, theirs 215). Automatic variable renaming from static analysis was "the single most impactful optimization, netting several hundred bytes". The weird hack: bits leaked through `randint` in tasks 043, 127 and 142 showed every ARC-GEN example used seed 2025 plus its index, and task 096's solution recovers the seed and replays the generator. Only one task qualified.

**Theoretical Syntax Golfers (6th)** reached 955,251 by hand and added 2,276 with compression. Variable names were optimised first by static analysis (liveness, interference graph, Optuna candidates), then by simulated annealing against the real zopfli byte count, each candidate checked on 10 test cases; the annealing, seeded by the static result, won.

**Santa Golf Club 2500 (9th)**, five competitive programmers with no golf background, hand-wrote every task over 1,000+ hours, learning from ChatGPT, Gemini and Claude without taking their code. Their dashboard ranked tasks by gap to the public best and staleness, to make teammates "chase" each other's partial ideas.

### LLM-centred workflows (7th, 15th, 19th)

**LogicLynx (7th)** decided five people could not hand-golf 400 tasks and built around Codex Web, which returns up to four results per prompt; review meant picking the shortest valid one. The context engineering transfers: code.golf wiki knowledge, tricks extracted by having the AI analyse their own near-optimal code, kept in `AGENTS.md`, and a per-task memo of tried experiments, cleared whenever code got shorter because old ideas may work again. A teammate's assessment: AI was strong on volume and tiny optimisations, weak on regex tasks. Humans contributed tricks like a Chinese Remainder Theorem single loop for task 240.

**santa2024 (15th)** ran hand, LLM, rule-based and compression tracks. Humans wrote initial solutions because, in their experience, LLMs could not solve from scratch or change algorithms. After GPT-5's release, GPT-5 Codex and GPT-5 Pro did follow-up golf on strong human seeds, often closing 50-point gaps to first place. Prompt files carried first-place-length examples, golf tips and translated hints for every task (published by a 13th-place member). A background API loop found a few-byte gain about once per 50 tasks with gpt-5, once per 100 with gpt-5-mini.

**Team (19th)**, one member's part: an evolutionary database per task, a propose-validate-minify loop, mostly gemini-2.5-flash on the free tier. Two findings are gold. arc-dsl solutions in the prompt capped progress because those shortcuts fail ARC-GEN's extra examples; removing them took the agent from about half the tasks to about 360. And too much context (10 I/O pairs, 8 exemplars, 10 priors) made the model drift, a clean case of [context rot](/blog/machine-learning/ai-agent/effective-context-engineering-for-ai-agents). It plateaued at about 0.940 on the author's normalised scale; the rest was manual.

### Hand golf with LLM assist (8th, 10th), and the contrasting entry

**import itertools (8th)** is the best contrast. A mostly non-expert team, their "first instinct was to lean heavily on LLMs. It didn't take long to realize it was not going to get us anywhere near the top." LLMs got them to 400 of 400; the rest was by hand: a rotate-and-recurse flood fill whose update expression pysearch found, four nested loops flattened into one with bit operations, hash-based special cases like `hash((*c,))%709==8`. After reading other writeups, jacekwl concluded the LLM ceiling is "much much higher, you just have to use them in a smart way". Put 7th and 8th side by side: one place apart, opposite conclusions, both honest. **lv1.dev (10th)** says only "a combination of manual golfing, with iterative refinement by LLM (mainly OpenAI Codex Web)".

### Tooling only (14th, 16th) and no writeup

**ALE-Agent (14th)** is Sakana AI's team; with no writeup, the repository shows a judge, a compressor, a variable-name optimiser and "prompt generators to easily paste prompts into ChatGPT or Claude". Whether Sakana's ALE-Agent system itself produced the code cannot be verified. **mystery+bono+Lucien (16th)** started from two public notebooks and added a compressor sweep and name optimiser. cam jam! (11th), ﾀｲｽｹﾝｻﾝﾊﾞII (12th), 暗黑AGI (13th), Golfers Anonymous (17th), Team JYCDT (18th) and ShadowPrompt Labs (20th) published no method, and their methods remain unknown.

## What LLMs did and did not contribute

| LLMs did | Evidence | LLMs did not | Evidence |
|---|---|---|---|
| Get to 400 of 400 quickly (0 to 1) | 8th, 15th, 2nd on long tasks | Find the reformulation that saves 10+ bytes | 15th, 7th, 3rd's prediction |
| Grind tiny optimisations at volume | 7th, 4th | Invent regex golf unprompted | 19th, 7th |
| Run cheaply in parallel against an exact verifier | 4th, 15th | Escape local optima on their own | 4th (fresh sandboxes), 15th |
| Write tooling (a GA renamer) | 2nd | Beat an expert's final file | podium vs 4th |

The split is between execution and invention. Where the reformulation is supplied (a human seed, a prompted regex, a known shorter length), the models grind well; where it must be invented, they stall. The 19th-place author puts it in their own terms: ARC's spatial rules make LLMs hallucinate. The [ARC Prize 2025 post](/blog/machine-learning/learn-from-kaggle/kaggle-arc-prize-2025-solutions) covers ARC from the solving side.

## What the forum taught everyone

- **The shared spreadsheet** of per-task scores became the benchmark every team chased.
- **Public trick lists and notebooks:** Tony Li's "TOP 78 Tricks" (18th), garrymoss's variable-name notebook, boristown's hints for all 400 tasks, and solution notebooks that seeded 16th.
- **Exploits and patches:** the `os.path.getsize` thread and the private report fixed on August 25.
- **The framing question:** Chris Deotte's "Solutions By Hand or Solutions By LLM?", answered by the final board.

No shake-up: with a 100% public board, final rank equals public rank for every top-20 team.

## What did not work

| Idea | Who reported it | Why it failed |
|---|---|---|
| Leaning on LLMs to reach the top tier | 8th | Saturated field |
| LLMs for algorithm changes, escaping local optima | 15th, 4th | Models anchor on the current solution |
| LLMs on regex tasks | 7th, 19th | Humans had to set the approach |
| arc-dsl solutions in the prompt | 19th | They fail ARC-GEN's extra examples |
| Large prompts (10 pairs, 8 exemplars, 10 priors) | 19th | Context rot |
| GA and annealing on Huffman trees | 5th | Rugged landscape; DP worked |
| lzma under ~1,000 bytes, bz2 | 5th | Header too big; BWT weaker |
| Aliasing builtins under compression | 15th | Repeated `range` compresses better |
| Trusting a local `==` check | 15th | Always-true `__eq__` fails on the server |
| Grok-4 in the agent loop | 4th | Tool misuse and cost |

## Lessons that transfer

1. **A verifiable task makes LLM loops cheap, not sufficient.** FuunAgent reached 4th; the last ten bytes per task belonged to experts (1st, 4th).
2. **Best-of-N, exact verification, rule-written critique.** Four samples, keep the shortest valid, let static analysis of the output pick the next hint (4th; 7th's four outputs per prompt).
3. **Reset the sandbox to escape anchoring; keep a memo of failures.** An agent that sees old solutions reproduces them (4th); a per-task memo, cleared on progress, stops repeats (7th).
4. **Optimise the real objective.** Bytes after compression, not raw bytes; repetitive code compresses better (1st, 5th, 4th's final weeks).
5. **Use search where fitness is free, matched to the landscape.** Fuzzers, GAs, annealing and pysearch (2nd, 3rd, 6th, 8th); DP for Huffman trees, annealing for names (5th vs 6th).
6. **Measure after untrusted code finishes.** The getsize exploit is a lesson for any leaderboard that runs submissions.

### If you enter a competition like this

- Solve everything first at any length; a wrong file costs ~2,400 points, a long one dozens.
- Validate every candidate on every generated example, and check output types.
- Build a per-task dashboard: your length, the public best, the gap, staleness.
- Write the compression stub and a name optimiser early; compress only past ~200 bytes.
- Run an LLM loop for breadth, with a memory of failed ideas and fresh sandboxes.
- Spend human hours on reformulations where the gap to the public best is largest. The [NeuroGolf 2026 post](/blog/machine-learning/learn-from-kaggle/kaggle-neurogolf-2026-solutions) covers the sequel, where what is minimised is a neural network.
